### The Parallel Implementation
The parallel version of the serial implementation of `SoloLevelling` was implemented by **parallelizing** the `Hunt` and `DungeonHunter` classes into `HuntParallel` and `DungeonHunterParallel` respectively. The `DungeonMapParallel` class serves as a fork of the `DungeonMap` class with differing semantics but identical functionality and structure.

Extract from `HuntParallel`:
``` Java
public class HuntParallel extends RecursiveTask<Integer>
{
    /** ... */

    /** Allows FindManaPeak() to be called concurrently on separate threads */
    @Override
    protected Integer compute()
    {
        return FindManaPeak();
    }

    /** ... */
}
```

Extract from `DungeonHunterParallel`:
``` Java
public class DungeonHunterParallel
{
    static class ComputeMaxHuntResult
    {
        /** ... */

        public int Value;
        public int Index;
    }

    static class ComputeHuntMaxTask extends RecursiveTask<ComputeMaxHuntResult>
    {
        /** ... */

        @Override
        protected ComputeMaxHuntResult compute()
        {
            int length = m_End - m_Start;
            if (length == 1) // Sequential Cutoff
            {
                m_Searches[m_Start].fork();
                return new ComputeMaxHuntResult(m_Searches[m_Start].join(), m_Start);
            }

            // Recursively split task into two halves
            int mid = m_Start + (m_End - m_Start) / 2;
            ComputeHuntMaxTask leftTask = new ComputeHuntMaxTask(m_Searches, m_Start, mid);
            ComputeHuntMaxTask rightTask = new ComputeHuntMaxTask(m_Searches, mid, m_End);

            leftTask.fork();
            ComputeMaxHuntResult rightResult = rightTask.compute();
            ComputeMaxHuntResult leftResult = leftTask.join();

            return (leftResult.Value >= rightResult.Value) ? leftResult : rightResult; // Return the max
        }

        private final HuntParallel[] m_Searches;
        private final int m_Start;
        private final int m_End;
    }
}
```

### Validation
To ensure a proper comparison between the *serial* and *parallel* implementations, an output validation technique had to be employed. However, due to the *benign race conditions* present in the *parallel* implementation, simply comparing textual output wasn't enough. To ensure the correctness of the *parallel* implementation, a short program named `ImageCompare` was written in `C++`, which was used to validate the *parallel* implementation against the *serial* implementation by means of the `CompareSearchMaps.py` python script:
``` Python
myDir = os.path.dirname(os.path.abspath(__file__))
projRoot = os.path.abspath(os.path.join(myDir, ".."))

subprocess.run(

    check = True, text = True)
print()
subprocess.run(
    ["make", "-C", "./ImageCompare", "run", "ARGS=../bin/Serial/visualiseSearchPath.png ../bin/Parallel/visualiseSearchPath.png"],
    check = True, text = True)
```

This script takes both search maps generated by the *serial* and *parallel* implementations respectively and passes them in pairs to `ImageCompare` which checks to see if each and every byte of the two respective images are exactly the same. If they are the same, the *parallel* implementation is valid, otherwise not. Here's how `ImageCompare` compares the images:
``` C++
static bool ImageCompare(const std::string& image1Path, const std::string& image2Path) noexcept
{
    size_t size1;
    uint8_t* image1 = ReadBytes(image1Path, size1);
    if (!image1)
    {
        std::cerr << "Failed to load image from: \"" << image1Path << "\"\n";
        return false;
    }

    size_t size2;
    uint8_t* image2 = ReadBytes(image2Path, size2);
    if (!image2)
    {
        std::cerr << "Failed to load image from: \"" << image2Path << "\"\n";
        delete[] image1; // Avoid memory leak on early-return

        return false;
    }

    if (size1 != size2)
    {
        std::cout << "Images have differing sizes!\n";
        return false;
    }

    // Compare each and every byte of the 2 images
    bool imagesEqual = true;
    for (size_t i = 0; i < size1; ++i)
    {
        if (image1[i] != image2[i])
        {
            imagesEqual = false;
            break;
        }
    }

    delete[] image1;
    delete[] image2;

    return imagesEqual;
}
```

### Optimum Search Density
Determining the **optimum search density** was done by writing a `Java` program named `SearchDensityProfiler`. This program works by testing every search density between `0-1` with a **step** of `0.05` at a constant **gate size** of `200` and **random seed** set to `627` - and measures each of these test 5 times. This profiler also considers **JVM warmup time** by running `3` tests before taking measurements and using the same instance of the **JVM** for all tests. It also manually invokes the **garbage collector** in-between tests to minimize any effects that caching may have on testing.

``` Java
// Warm-up phase
for (int i = 0; i < WARMUP_ITERATIONS; ++i)
    RunTest(i, null); // Pass a null writer to ignore these timings

for (int i = 0; i < SEARCH_DENSITIES.length; ++i)
{
    for (int j = 0; j < MEASURE_ITERATIONS; ++j)
    {
        RunTest(i, writer);
        System.gc();
    }
}
```

The profiler then writes the results of these tests to a **CSV** file which can be used to plot a graph in `python` using `matplotlib`. We can then identify the **optimal search density** for a specific machine by reading the 'highest' point on the graph.

### Benchmarking
Benchmarking was handled by writing a `Java` program named `Profiler`. Similarly to `SearchDensityProfiler`, this program also considers **JVM warmup time** and runs `3` warmup iterations before taking measurements while also using a **random seed** of `627` and invokes the **garbage collector** between tests. The `Profiler` runs tests starting from a **minimum gate size** of `20` up to a **maximum gate size** of `200` - measuring each test `10` times. The `Profiler` uses the **optimal search density** determined by the `SearchDensityProfiler` for all tests.

``` Java
// Warm-up phase here
for (int i = 0; i < WARMUP_ITERATIONS; ++i)
    RunTest(i, MIN_GATE_SIZE, SEARCH_DENSITY, null); // Pass a null writer to ignore these timings

for (int gateSize = MIN_GATE_SIZE; gateSize < MAX_GATE_SIZE; gateSize += GATE_SIZE_STEP)
{
    for (int i = 0; i < MEASURE_ITERATIONS; ++i)
        RunTest(i, gateSize, SEARCH_DENSITY, writer);
}
```

The profiler then writes the results of these tests to a **CSV** which can be used to plot two sets of graphs in `python` using `matplotlib` - one being the results from *Nightmare*, and the other being from any other machine.

Benchmarking was performed on:
- 4-Core AMD Ryzen 3 7320U
- Nightmare server (via SSH)
- 6-Core Intel I5-9400F (only for reference, not included in final results)

In this experiment the **sequential cutoff** was deliberately set to `1` to isolate and measure the pure overhead and scalability of the `ForkJoin` parallel decomposition. By forcing every individual element to be handled as a *separate task*, the algorithm maximizes *task granularity* stressing the parallel framework however, in practice, a *larger cutoff* would likely yield much better performance.
